# 選做｜各 Lab 的 Prompt 風格對照

同一個任務，可以用模糊、精準、驗收導向或分階段的 prompt，觀察 Copilot 的範圍判斷、修改與驗證方式。以下提供可貼用的版本，不取代 [Lab 手冊](labs.md) 的標準流程與完成條件。

**本文列出的差異是待觀察的假設，尚未實際執行對照實驗；精準 prompt 也不保證結果正確。** 課中可由不同組別各選一個版本，課後再重複比較；不要求每人跑完所有版本，不延長原本 90 分鐘。

## 使用方式與固定條件

每次先貼以下共用前綴，再貼選定的版本。模糊版本只減少任務細節，不取消專案規範：

```text
請遵守根目錄 AGENTS.md，以 docs\rules.md 為正確性來源，
只處理下方指定的 Lab。
執行命令時使用 docs\setup.md 已確認的 Python interpreter。
未實際執行的檢查須明確標示未驗證。
```

專案限制統一維護於 [AGENTS.md](../AGENTS.md)，不因版本不同而放寬。需要命令時，使用 [Lab 手冊](labs.md) 中對應的 Windows PowerShell 或 Linux／macOS Bash／Zsh 區塊。

1. **相同起點：** 各版本使用不同資料夾中的相同 Lab 起始內容，不在 A 修改後的程式上直接跑 B，不 reset 或覆寫原作業。Lab 2 必須使用同一份 Lab 1 成果；測試比較必須使用同一份已確認的 review 結論。
2. **相同上下文：** 固定模型、Chat session 類型、agent、工具權限、專案指引、附加檔案與證據。各開新 Chat，避免前一版本的討論影響下一版本。
3. **相同驗收：** 不論 prompt 是否列出驗收細節，人工都依相同的業務規格與 Lab 完成條件核對。只確認模型回覆「完成」不算驗收。
4. **保留第一輪：** 先記錄第一次結果，再補充需求或糾正方向；把後續提示、返工與人工確認時間也記入成本。

同一 Lab 的各版本提供相同材料；必要時手動附加，不假定 Copilot 自動取得終端機、diff 或瀏覽器內容：

| 比較範圍 | 共用上下文（另含 AGENTS.md 與 docs\rules.md） |
|---|---|
| Lab 1A Coding | `shipping.py`、`app.py`、`templates\index.html`、`static\app.js` |
| Lab 1B Review | 同一份快捷服務 diff、相關核心／API／前端檔案與既有測試 |
| Lab 1C Test Case | `shipping.py`、`tests\test_shipping.py`、同一份已確認的 review 結論 |
| Lab 2 UI/UX | `templates\index.html`、`static\styles.css`、`static\app.js`；若提供改善前畫面，各版本使用相同畫面 |
| Lab 3 RPA | `rpa\track_mail.py`、`templates\tracking.html`、`static\tracking.js`、同一份日誌與輸出、`fixtures\tracking.json`、`fixtures\expected_summary.json` |

使用唯讀 custom agent 時，各版本都維持唯讀，不為某一版本開放額外工具。需要執行重現時由學員操作並提供結果；需要修正時明確切換至具備編修工具的 agent。切換方式也須一致。

## Lab 1A｜Coding：新增快捷服務

**共同任務：** 完成快捷服務的核心計算、API 與網頁選單，保留一般、掛號功能。

### A. 模糊／結果簡述型

```text
請幫這個寄件試算工具加入快捷服務，
讓使用者可以在網頁上選擇並試算。
```

**觀察：** 是否主動查規格？是否只新增選單而漏掉計算？是否猜測加價或自行擴大範圍？是否主動驗證？

### B. 精準／規格型

```text
請閱讀 docs\rules.md、shipping.py、app.py、
templates\index.html 與 static\app.js。

新增 express 快捷服務，加價 30 元，與 standard、registered 三選一。
完成核心計算、API 可用性及網頁選單串接。
保留既有 API 格式與一般、掛號行為，不新增套件或重寫專案。
其他不直接相關的缺陷只記錄；必要的連帶修正請解釋原因。

執行既有測試，並核對 1000 公克：
standard 為 60、registered 為 80、express 為 90。
```

**觀察：** 是否完整串接三個層次？修改是否集中？是否把三個正常案例通過誤當成所有邊界都正確？

### C. 驗收導向／不指定解法型

```text
請依 docs\rules.md 完成快捷服務，修改方式由你判斷。

完成條件：
- 網頁可以選擇 express，不能與其他服務疊加。
- POST /api/quote 在 1000 公克、express 時回傳 HTTP 200，
  內容為 {"fee":90,"currency":"TWD"}。
- 1000 公克的一般、掛號仍分別為 60、80 元。
- 非法輸入符合既有 API 契約，不因新增服務而放寬驗證。

請以最小必要變更完成，提供各項完成條件的驗證證據。
無法實際操作網頁時，明確列出待人工驗收項目。
```

**觀察：** 不給實作步驟，是否仍能找齊相關檔案？是否以契約而非「程式能跑」判斷完成？

### D. 分階段／先理解再實作型

第一輪：

```text
先不要修改。
閱讀快捷服務需求與相關程式，列出：
1. 使用者選擇服務後，資料如何從網頁流向 API 與核心計算。
2. 預計修改的檔案，以及每個檔案的修改理由。
3. 如何證明快捷可用且既有服務沒有退化。
不要延伸到其他功能，等我確認範圍再實作。
```

人工確認後，第二輪：

```text
依剛才確認的範圍實作快捷服務。
若實際發現需要額外修改，先說明它與本需求的直接關係。
完成後依確認的驗收方式核對結果。
```

**觀察：** 是否降低遺漏或過度修改？多一輪確認是否值得？耗時須包含人工確認時間。

**共同驗收：** 使用 Lab 1A 的網頁、API 與報價檢查點，不要求此階段完整修復所有既有邊界缺陷。C 額外強調非法輸入，若因此發現並修正直接相關缺陷，記錄修改範圍與理由，不把額外完成項目混成所有版本的必做條件。

## Lab 1B｜Code Review：檢查功能與缺陷

**共同任務：** 審查同一份 Lab 1A 成果；所有版本保持唯讀，不把 review 品質和自動修正能力混在一起。

### A. 模糊型

```text
請 review 剛才新增的快捷服務，看看有沒有問題。
只分析，不修改檔案。
```

### B. 精準／範圍型

```text
請 review 快捷服務變更及直接相關的既有計算、API 與輸入驗證路徑。
只分析，不修改，不要只看 diff 而忽略被呼叫的既有程式。

依 docs\rules.md 檢查：
服務互斥、費率級距、重量上下限、非法型別與前後端一致性。
不提供純風格建議，不為了湊數編造缺陷。

每項發現附檔案與行號、觸發輸入、預期與實際結果、影響及修正方向，
區分既有缺陷與本次引入的問題，以及已重現與推測。
```

### C. 證據導向型

```text
只做唯讀 review。
請嘗試用最小輸入證明本次功能或直接相關路徑違反 docs\rules.md。

每項結論分成：
- 已重現：提供輸入、執行方式與實際結果。
- 待驗證：說明推測依據與下一個最小驗證步驟。

工具不能執行時，提供由我操作的步驟，不要宣稱已重現。
沒有發現問題時，列出已檢查範圍與尚缺的測試即可。
```

**共同驗收與比較：** 人工重現並核對結論；記錄成立的發現、誤報、是否漏看被呼叫程式，以及是否區分推測與事實。沒有缺陷時可記錄已通過與未覆蓋範圍，不要求硬湊問題。問題列得多不代表 review 比較好。

## Lab 1C｜Test Case：把缺陷轉成回歸測試

**共同任務：** 先新增測試，再依確認的失敗案例修正。比較第一階段時，各版本都不修改實作。

### A. 模糊型

```text
請幫郵資計算補一些測試。
本輪只修改測試，不修改實作。
```

### B. 精準／案例型

```text
閱讀 docs\rules.md、tests\test_shipping.py 與已確認的 review 結論。
只新增 tests\test_shipping_regression.py，不修改實作。

用 pytest 參數化優先覆蓋已重現缺陷，並涵蓋：
- 重量 1、1000、1001、2000、20000。
- 0、負數、20001、浮點數、布林值、字串與 None。
- standard、registered、express 及未知、空字串、非字串服務。

預期值必須由規格推導，不能呼叫被測函式產生預期值。
執行新增測試，區分實作缺陷與測試本身的錯誤。
不要放寬斷言來取得全綠。
```

### C. 需求追溯／測試設計型

第一輪：

```text
先不要寫程式。
將 docs\rules.md 與已確認的 review 發現整理成測試矩陣：
需求、輸入類別、邊界、預期結果、現有測試、缺少的測試。

優先選出能抓到已重現缺陷的案例，說明每個案例能辨識哪種錯誤。
預期結果不能從目前實作推導，等我確認矩陣再新增測試。
```

確認後，第二輪：

```text
依確認的矩陣新增 tests\test_shipping_regression.py。
同類案例使用 pytest 參數化；本輪不修改實作。
執行新增測試，說明失敗對應哪項需求或已確認的 review 發現。
不要放寬斷言來取得全綠。
```

**共同驗收與比較：** 檢查測試是否抓到已知缺陷、需求覆蓋與斷言是否獨立正確。先記錄測試階段成果，再使用 Lab 1C 相同的修正流程。不以測試數量或全綠作為唯一分數；若缺陷早已修正，依 Lab 手冊由講師提供獨立錯誤副本證明測試效力，不破壞自己的成果。

## Lab 2｜UI/UX：從好看到降低操作錯誤

**共同任務：** 改善同一份寄件試算頁，不改費率規則。三個版本共用以下範圍限制，與共用前綴一起貼上：

```text
只修改 templates\index.html、static\styles.css 與 static\app.js。
保留 API、DOM id 與主題變數，不新增 UI 框架，不改 RPA 查詢頁。
```

### A. 模糊／美感型

```text
請讓寄件試算頁面更好看、更好用。
```

### B. 使用情境型

```text
使用者是每天反覆試算的內部作業人員。
請改善寄件試算頁，優先降低：
輸入錯誤、重複送出，以及把舊報價誤當成新結果的風險。

說明每項設計解決哪個操作問題。
```

### C. 精準／可測量型

```text
請改善寄件試算頁，完成以下驗收：
- 重量有 label、單位與合法範圍；錯誤與欄位建立無障礙關聯。
- 不用滑鼠，Tab、Enter 可完成試算，焦點清楚。
- 375px 寬度沒有水平捲動。
- 請求中防止重複送出；HTTP 或網路失敗後恢復操作。
- 修改輸入後清除或標示舊報價失效。

區分已實際驗證與需要人工瀏覽器驗收的項目。
```

**共同驗收與比較：** 使用 Lab 2 相同的鍵盤、錯誤輸入、375px、離線、重複送出與舊報價操作，以及既有費率測試。觀察 A 是否主要換色與排版、B 是否從情境推導防呆、C 是否逐項達標；不只評畫面漂亮程度。沒有瀏覽器工具時由學員人工操作，不把單元測試通過當成 UI 驗收。

## Lab 3｜RPA：從跑得完到資料正確

**共同任務：** 診斷並修正同一份本機 RPA。三個版本共用以下範圍限制，與共用前綴一起貼上：

```text
只修改 rpa\track_mail.py，保留 query_status 介面與 CLI 輸出格式。
不修改查詢頁、fixtures、預期結果或 requirements。
```

### A. 模糊／症狀型

```text
這個本機郵件查詢 RPA 有時失敗，跑完的資料也可能不對。
請找出原因並修好。
```

### B. 精準／限制型

```text
請根據 rpa\track_mail.py、失敗日誌、查詢頁 DOM 與 fixtures 診斷問題，
再以最小變更修正等待條件與欄位定位。

等待上限使用 timeout_ms，不增加固定 sleep、無限重試或吞掉例外。
核對回傳郵件編號，區分查無資料、逾時與頁面錯誤。
不要以空白結果或部分成功摘要冒充成功。
```

### C. 假設驗證／先診斷型

第一輪：

```text
先不要修改。
根據相同程式、日誌、DOM 與 fixtures，分別分析：
1. 查詢尚未完成就讀取結果。
2. 腳本正常結束，但摘要內容不正確。

每個可能原因列出支持證據、尚缺證據與最小驗證步驟。
不要先假定只有一個原因，也不要把結束碼 0 當成資料正確。
等我核對分析與驗證結果再修正。
```

確認後，第二輪：

```text
只以最小變更修正已確認的根因。
等待上限使用 timeout_ms，不增加固定 sleep、無限重試或放寬成功判定。
核對欄位內容與郵件編號，區分查無資料、逾時與頁面錯誤。

驗收 1200ms、1800ms 延遲的摘要均符合獨立預期結果；
逾時及 MISSING 均須結束碼 1、ok:false，並提供失敗編號與明確原因。
不能實際執行瀏覽器時，標記尚未驗收。
```

**共同驗收與比較：** 三個版本都使用 Lab 3 完整的成功與失敗驗收。觀察是否只拉長固定等待、是否定位到正確欄位與編號、不同延遲下是否資料一致，以及失敗時是否留下成功形狀的輸出。摘要單元測試通過不等於瀏覽器等待與定位正確；只分析預錄證據時須記錄尚未執行驗收。

## 比較結果怎麼記錄？

先比較模糊型與精準型，有時間再加入第三種風格。每個版本使用 [作業單](worksheet.md) 的「Prompt 對照」區塊記錄：

| 指標 | 判定方式 |
|---|---|
| 正確性 | 第一輪與最終結果各通過哪些獨立驗收項目，哪些失敗或未驗證 |
| 範圍控制 | 是否修改不相關檔案、規格、fixtures 或超出任務 |
| 證據品質 | 是否提供可核對結果，是否把推測或未執行事項說成已驗證 |
| 人工介入 | 補充需求、糾正方向與返工次數，保留後續 prompt |
| 成本 | 耗時與互動輪數，包含人工確認；介面有資料時再記錄用量 |

同一版本可重複 2–3 次，逐次記錄，不只挑最好的一次。只有一次結果時，稱為課堂觀察，不宣稱某種風格必然更好。這些版本有的同時改變細節量、驗收強度與工作流程；若要判斷單一因素，需另做一次只改一項的比較。

**模糊 prompt 仍可能因 AGENTS.md、附加規格或模型主動探索而表現良好。真正影響結果的是完整上下文，不只是最後貼出的那句話。**
