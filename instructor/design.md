# 中華郵政 GitHub Copilot 本機開發 Workshop

> 講師課程設計，包含教學缺陷說明。學員請使用根目錄 [README](../README.md)，不要將本文件交給 Copilot 作答。

## 課程定位

以「郵務寄件作業小幫手」貫穿三個 Lab：第一個 Lab 串起 Coding → Code Review → 自動補測試案例與修正，第二個聚焦 UI/UX，第三個聚焦 RPA 問題查找。

第一個 Lab 的三個階段沿用同一份需求與同一組程式變更，形成完整的開發與品質驗證流程，不拆成互不相關的練習。UI/UX 可延續完成的功能；RPA 則使用獨立模擬頁，各自保有可單獨開始的教材。

**總長 90 分鐘，包含操作切換與收尾，不包含課前安裝。** 說明簡報沿用既有版本，現場以實作為主，不再安排長篇產品介紹。

本 repository 包含 **可執行起始專案、學員手冊與講師資源**。學員直接 clone，根目錄程式為故意保留缺陷的 Lab 1 起點；`instructor` 保留供講師維護使用，學員與 Copilot 不應讀取或搜尋此目錄找答案。此規範不構成存取隔離。

### 對象與學習成果

適合具備基本程式閱讀能力，但不一定熟悉 Python 或網頁開發的學員。程度差異較大時，採兩人一組：一人操作、一人檢查需求與結果。

完成後，學員應能：

- 提供明確的檔案、需求與錯誤資訊，讓 Copilot 在限定範圍內工作。
- 區分「看起來合理的建議」與「有重現步驟及證據的問題」。
- 審閱程式差異，執行程式或測試，而非直接接受所有生成內容。
- 用需求與獨立的預期結果檢查測試品質，避免讓 AI 用錯誤實作反過來定義正確答案。

## 情境與技術選擇

情境：內部作業人員需要輸入包裹重量與寄送服務，試算費用；另有一支 Python RPA，會從模擬郵件查詢網頁擷取狀態並產生本機作業摘要。

| 項目 | 設計 |
|---|---|
| 開發介面 | VS Code＋GitHub Copilot Chat；以詢問／唯讀分析與 Agent 編修為主 |
| 應用程式 | Python＋Flask；HTML、CSS 與少量原生 JavaScript |
| RPA | Python＋Playwright，操作本機模擬查詢頁 |
| 測試 | pytest；核心邏輯以單元測試驗證，RPA 另設本機瀏覽器驗收 |
| 資料儲存 | 教學用 JSON fixtures，不使用資料庫 |
| 執行方式 | 應用程式與瀏覽器自動化均在學員本機執行 |
| 不納入 | 雲端部署、GitHub Actions、正式系統串接、真實帳號、付費 API、額外 MCP 設定 |

**本機執行不等於離線使用。** Copilot 仍需組織允許的網路連線與使用授權；提供給 Copilot 的內容須遵守組織政策。只使用虛構郵件編號與教學資料，不使用客戶資料、正式郵務資料、憑證或內部正式系統截圖。

RPA Lab 教的是「從日誌、畫面與程式找根因」的方法，不是 UiPath 或 Power Automate 的平台操作課程。

## Lab 1：Coding → Code Review → 自動補測試案例（45 分鐘）

**任務：** 為寄件試算新增快捷服務，審查剛完成的變更及其依賴的費率邏輯，再把 review 發現轉成測試、修正與回歸保護。

起始教材支援一般與掛號，基準測試通過，但保留兩個未涵蓋的既有缺陷：重量上限的邊界判斷錯誤，以及未拒絕零／負重量。學員先新增快捷服務，再檢查完整計算路徑；不是預先假定 Copilot 產生的程式一定有錯。

| 階段 | 交給下一階段的成果 |
|---|---|
| A. Coding | 可操作的快捷服務、程式差異與執行結果 |
| B. Code Review | 已驗證缺陷或風險清單、觸發輸入與預期行為 |
| C. 補測試與修正 | 對應需求與 review 發現的測試、修正後結果 |

### A. Coding：先完成一個功能

新增快捷服務，並讓網頁可以選擇此服務。範圍限於既有計算函式、必要的 API 處理及服務選單，不新增框架或重寫整個專案。

**操作順序：** 拆解需求、生成與閱讀差異、執行正常情境。

```text
請閱讀 docs/rules.md 與目前費率計算、API 和表單的實作。
先用簡短清單指出需要修改的檔案，再依需求進行修改：
1. 新增 express 快捷服務，加價 30 元，與其他服務互斥。
2. 前後端都能處理快捷服務；沿用既有錯誤呈現方式。
保留既有一般與掛號行為，不新增相依套件，不修改業務規格。
完成後執行既有測試，核對 1000 公克的一般 60 元、掛號 80 元、快捷 90 元。
如果發現其他缺陷，明確記錄；與本次功能直接相關的修正請說明原因。
若需求不明確，先指出，不要自行改變費率。
```

**階段驗收：** 重新整理網頁後可選快捷服務，三個正常情境符合規格，既有測試通過。學員能指出前後端如何串接，並解釋至少一段接受的差異。此時通過不代表所有邊界已正確，仍需後續 review 與測試。

### B. Code Review：檢查剛完成的功能

切換為唯讀分析，對照需求檢查階段 A 的差異與相關既有邏輯，不立即修改。可開新的 Chat，明確附上需求、差異及相關檔案，避免只讓 Copilot 延續先前的實作理由。

**操作順序：** 說明範圍、Copilot 分析、人工重現與討論。

```text
請 review 本次新增快捷服務的程式差異，以及 shipping.py、API 與表單中
直接相關的計算和輸入驗證路徑，先不要修改檔案。
依據 docs/rules.md，檢查功能是否完整、既有行為是否被破壞、邊界與錯誤處理是否正確。
不需要命名或排版建議，也不要為了湊數提出問題。
每個問題請提供：檔案與行號、觸發輸入、預期與實際行為、影響及修正方向。
區分本次引入的問題與既有缺陷，以及已驗證問題與推測。
若可執行，請用最小範例重現；最後列出應補哪些回歸測試。
```

**階段驗收：** 學員確認 review 結論與重現結果相符，並將已確認問題交給階段 C。若回覆漏掉邊界，追加「請檢查最小值、最大值及前後一個單位」，不要直接提供答案。

若階段 A 已修正預埋問題，review 應確認修正並找出仍缺少的回歸測試，不要求硬湊兩個缺陷。講師另提供獨立的 review 練習副本，讓沒有剩餘缺陷的組別仍可體驗問題重現；不可把缺陷重新塞回學員的成果。

### C. 自動補測試：把 Review 發現變成回歸保護

優先針對階段 B 的問題建立測試，再補需求邊界。對尚未修復的問題先確認測試失敗，再修正實作並重跑，完成「發現 → 證明 → 修正」。

**操作順序：** 確認測試矩陣、生成與執行測試、最小修正與重跑。範圍限制為小型費率函式的缺陷；若卡關，使用階段救援快照接續。

```text
請閱讀 docs/rules.md、目前 tests 與剛才已確認的 review 結果，
建立精簡的需求／問題／測試對照表。
預期值必須由規格推導，不可呼叫被測函式來算自己的預期結果。
先只補 pytest 測試，不修改實作，優先涵蓋：
- review 已重現的缺陷。
- 重量 1、1000、1001、2000、20000 的邊界。
- 重量 0、負數、20001、非整數與布林值。
- 三種服務的費用與未知服務。
同類輸入使用參數化測試，測試應可重複執行，不使用外部網站。
執行後區分預期的缺陷失敗與測試本身的錯誤，不可放寬斷言讓結果通過。
說明仍未涵蓋的需求，不以測試數量或覆蓋率代替正確性。
```

確認測試失敗原因後，再進行下一輪：

```text
請依據已確認的失敗測試與業務規格，最小幅度修正實作。
不得修改業務規格或放寬測試斷言；保留快捷服務與既有功能。
重新執行既有及新增測試，說明每項修正對應哪個 review 發現。
```

**Lab 1 完成標準：**

- 固定驗收資料全部符合，快捷服務可從網頁操作。
- 後端也會拒絕非法重量，以直接 API 呼叫確認，不只依賴前端驗證。
- 新測試涵蓋合法邊界、非法輸入與服務差異，且學員能說明至少一個預期值來源。
- 至少一個新增測試在修正前失敗、修正後通過，失敗原因符合預期。
- 若缺陷已在階段 A 修復，使用獨立的已知錯誤副本證明測試能攔截問題，不覆寫學員成果。

本 Lab 不包含 RPA 測試，避免提前引入另一個情境。進階學員可補 API 契約測試或檢視覆蓋率，均不列入必做範圍。

## Lab 2：用可驗收的要求改善 UI/UX（15 分鐘）

**任務：** 改善同一個寄件試算頁，重點是作業效率與防呆，不是只換配色，也不重現官方品牌介面。

**操作順序：** 找出操作問題、修改、以瀏覽器人工驗收。

```text
請改善寄件試算頁，只修改 HTML、CSS 與必要的前端互動。
使用者是需要反覆輸入資料的內部作業人員。
請保留既有 API、費率邏輯及既有 DOM id／測試定位屬性，不新增 UI 框架。
必做要求：
- 重量欄位有明確 label、單位及範圍提示。
- 錯誤顯示在相關欄位附近，不只用紅色表示，並可由輔助科技識別。
- 用 Tab、Enter 可完成試算，焦點位置清楚。
- 送出期間避免重複送出，結束後恢復可操作狀態。
- 顯示試算結果後若輸入改變，清除或標示舊結果，避免誤用。
- 在 375px 寬度下主要內容不產生水平捲動。
不要修改 RPA 的模擬查詢頁。完成後列出需要人工驗證的項目。
```

**驗收：** 學員親自執行一次鍵盤操作、非法輸入、成功試算、修改輸入與窄螢幕檢查。網路或伺服器錯誤不得留下永久停用的送出按鈕。

本單元不依賴 Copilot 自動看見瀏覽器；需畫面資訊時提供不含敏感資料的截圖。沒有瀏覽器自動化工具也能完成。

## Lab 3：RPA 問題查找與修復（18 分鐘）

**任務：** 修復一支查詢模擬郵件狀態的 Python RPA。先重現、讀日誌、找根因，再修改；不要把「拉長 sleep」當成完成。

教材提供獨立的本機查詢頁與三筆虛構郵件。預埋兩個可重現問題：

- 查詢結果延遲載入，RPA 使用不足的固定等待，導致讀取不到結果。
- 查詢表格新增欄位後，RPA 仍以欄位位置讀取，抓到錯誤的狀態內容。

模擬頁應使用可控的載入延遲，而非不可重現的隨機錯誤；提供穩定的語意或測試定位屬性供修正使用。

**操作順序：** 重現與收集證據、定位與修復、重新執行驗收。

```text
請協助診斷 rpa/track_mail.py，只操作本機模擬查詢頁。
先閱讀腳本、fixtures、錯誤日誌與查詢頁 DOM，暫時不要改程式。
請列出觀察到的事實、可能根因，以及驗證各根因的最小步驟。
完成重現後，以最小變更修正等待條件與資料定位問題。
不要用增加固定 sleep、無限重試、吞掉例外或空白成功結果來繞過問題。
若查不到郵件或逾時，須清楚回報對應編號與原因。
保留既有輸出格式，修正後比對 fixtures 中的預期結果。
```

**驗收：**

- 三筆郵件的編號與狀態均符合獨立的預期 fixture，不只確認腳本結束碼。
- 在兩種載入延遲設定下，各完整執行一次並得到一致結果。
- 將等待上限設成小於模擬延遲，確認會明確失敗，不輸出成功摘要。
- 加入不存在的郵件編號，確認能區分「查無資料」與「尚未載入」。

RPA 查詢頁與 Lab 2 試算頁必須分開，避免 UI 練習意外改掉故障情境。只能分析預錄日誌的學員可完成根因分析，但不能宣稱已完成實際修復驗收。

RPA 摘要的 fixture 單元測試由教材預先提供，供修正後回歸確認，不另安排補測試任務。等待條件與 DOM 定位仍須由本 Lab 的瀏覽器驗收確認，不能宣稱 mock 測試已涵蓋。

## 選做：Copilot 客製化

新增 [選做手冊](docs/optional-customization.md)，讓有餘裕的學員修改一項設定並比較行為，不要求每項都操作：

- `AGENTS.md`：精簡的共用專案指引，練習新增規則與確認載入情況。
- `.github\agents`：預定義的唯讀程式 reviewer 與 RPA 診斷員，練習角色與工具範圍。
- `.github\skills`：手動啟用的測試設計與 RPA 證據分析流程，附資源模板。
- `.github\prompts`：Local Chat 可使用的重用 prompts；其他 session 使用 agent／skill 替代。
- `.github\instructions`：限定測試檔案的條件式指引。

這些設定會包含在所有匯出的教材包，不包含講師解答。必做課程不要求選取 custom agent 或啟用 skill；功能是否被 VS Code 發現、載入及遵守，須由講師於實際版本確認。

### Checkpoint 與救援方式

學員 clone 後從根目錄開始，正常情況延續自己的程式，不需生成或切換快照。講師可按需建立各 Lab 的獨立救援副本，避免前一個 Lab 阻塞後續操作；副本放到不同資料夾，不產生 ZIP，也不要求學員執行會丟棄修改的 Git 重設命令。

| 快照 | 必須具備的狀態 |
|---|---|
| Lab 1 起點 | 一般與掛號可操作、基準測試通過、保留兩個費率缺陷，尚無快捷 |
| Lab 1 階段 B 救援 | 快捷已串接、附功能變更差異、保留可 review 的邊界缺陷 |
| Lab 1 階段 C 救援 | 沿用階段 B 程式，附已確認問題與重現資料，但尚未補回歸測試 |
| Lab 2 起點 | 費率缺陷已修復、快捷可用、費率測試完整，介面仍待改善 |
| Lab 3 起點 | 獨立故障 RPA、模擬頁、日誌、fixtures 與摘要單元測試 |
| 講師驗證副本 | 已知錯誤版本，供 review 重現及證明新增測試可攔截回歸 |

若學員卡住，依序提供「縮小上下文的提示」、「指定問題檔案」、「切換下一 Lab 起點」。不要讓單一環境或生成問題耗掉後續主題。

## 成果展示與收尾

以五個具體問題確認學習成果，選做內容不列入必做完成標準：

- Coding：快捷服務是否真的從網頁一路連到後端計算？
- Review：哪個問題被實際重現，而不是只相信 Copilot？
- 測試：哪個新增案例確實抓到 review 發現或已知錯誤版本？
- UI/UX：哪個改動降低了輸入或誤用舊結果的風險？
- RPA：修的是等待條件與定位根因，還是只是增加等待時間？

核心訊息：**提供上下文 → 限定任務 → 審閱變更 → 用獨立標準驗證。**
